# Architecture

## How the system works

The bot is a real-time pipeline that turns a phone call into a back-and-forth conversation between a simulated patient and Pretty Good AI's scheduling agent. **Twilio** places the outbound call and streams the audio both directions over a WebSocket (mulaw 8 kHz, the telephony format). Incoming agent audio is forwarded to **Deepgram**, which transcribes it in real time and emits an end-of-utterance signal when the agent finishes a turn. That transcript, plus the active persona's instructions and the running conversation history, goes to **Groq** (`llama-3.3-70b-versatile`), which acts as the patient's brain: it produces the next thing the patient would say and decides whether the call should end. The reply is synthesized by **ElevenLabs** (`eleven_turbo_v2_5`) directly to mulaw 8 kHz and streamed back to Twilio. A small local WebSocket server bridges Twilio and the pipeline, exposed to the internet via **ngrok**. After each call, the transcript is saved, the recording is downloaded from Twilio as MP3, and a separate LLM pass writes an automated bug analysis. Personas are plain data objects (name, voice, scenario, instructions, and the specific behavior being tested), so new test cases need no code changes.

## Key design decisions

**Turn-taking is event-driven, not timed.** The hardest part of a phone bot is knowing when it's your turn. An early version replied after a fixed silence threshold, which made the bot talk over the agent and chop its own sentences. The bot now waits on Deepgram's `UtteranceEnd` signal and tracks whether the agent is mid-speech, so it only speaks once the agent has genuinely finished. I also tried full "barge-in" (cutting the bot off the instant the agent starts talking) but reverted it — over a noisy phone line it was too aggressive and truncated the bot's own replies, which made the agent repeat itself and polluted the transcripts. A clean wait-then-speak turned out to produce far more usable calls than a clever-but-fragile interrupt.

**The brain decides when to end, not a script.** Rather than hardcoding "after N turns, hang up," the LLM returns a small structured signal each turn (`say` / `end` / `reason`) and is told the elapsed call time, so it wraps up naturally once its goal is met and bows out gracefully on dead air. This keeps calls human-like and avoids both runaway loops and abrupt cut-offs.

**Model and voice were chosen for latency, then corrected for quality.** Because lag is what breaks the illusion of a real conversation, I favored Groq for its speed and ElevenLabs' turbo TTS. I started on a small model for speed, but it made reasoning slips (e.g. confirming the wrong name), so I moved up to the 70B model — fast enough to keep pace, smart enough to stay in character and catch the agent's mistakes. Mulaw 8 kHz output is requested directly from both Deepgram and ElevenLabs so no audio re-encoding is needed in the hot path.

**Automated analysis, human-reviewed findings.** Each call is auto-analyzed by an LLM against that persona's specific test goal, producing a first-pass bug list. Those are then human-reviewed and consolidated into the final bug report — the automation surfaces candidates quickly, but a person decides what's a real, well-described issue versus transcription noise.
